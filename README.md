|---|---|

## 1. 배경

쇼핑몰 고객 응대에서 전화 상담은 여전히 큰 비중을 차지한다. 배송 조회, 취소와 반품, 입금 확인처럼 같은 유형이 반복되는 문의가 대부분이지만, 전화는 상담원이 한 명씩 직접 받아야 한다. 그래서 응대 가능한 시간이 상담원 근무 시간에 묶이고, 문의가 몰리는 시간에는 대기가 길어진다. 상담원 인력을 늘리는 것만으로는 이 문제를 풀기 어렵다.

AI 상담원이 전화를 받으려면 두 가지 조건을 함께 갖춰야 한다. 첫째는 대화의 속도다. 전화에서는 2~3초만 말이 없어도 손님이 통화가 끊긴 것으로 여기고, 응답이 늦을수록 손님의 불만이 커진다. 둘째는 처리의 정확성이다. 브랜드마다 정해진 응대 절차와 정책이 있고, 주문 조회나 반품 접수처럼 실제 시스템을 다루는 일은 손님이 불러 준 번호 하나만 틀려도 잘못된 처리로 이어진다. 손님의 말에는 줄임말과 구어가 섞여 있고, 전화번호와 주문번호도 말로 불러 주기 때문에 받아쓰기 오류까지 감당해야 한다.

빠르게 답하는 것과 절차를 정확히 지키는 것은 서로 부딪히기 쉽다. 이 과제는 실제 쇼핑몰의 상담 시나리오과 상담 데이터를 바탕으로, 두 조건을 함께 만족하는 전화 상담 AI를 만드는 것을 목표로 한다.

## 2. 목표

손님이 전화로 말하면, 말이 끝나자마자 목소리로 답하면서 상담 시나리오를 정확히 지키는 AI 상담원을 만든다. 다음 세 가지를 동시에 달성해야 한다.

1. **속도.** 손님 말이 끝난 뒤 가능한 한 빨리 첫 소리를 낸다. 1.5초 안이면 속도 점수 만점이고, 4초면 절반, 6초를 넘기면 0점이다. 주문 조회처럼 함수를 부르는 문항은 조회 결과를 받은 뒤 실제 답을 시작하기까지의 시간도 따로 점수를 매긴다(3.5초 안이면 만점, 8초를 넘기면 0점).
2. **응대 품질.** 주어진 상담 시나리오의 흐름을 지키고, 가격·정책·조회 결과 같은 사실을 틀리지 않으며, 사람 상담원에게 넘겨야 할 때를 정확히 판단한다.
3. **정확한 처리.** 손님이 불러 준 전화번호와 주문번호를 정확히 받아, 맞는 기능을 맞는 값으로 호출한다.

## 3. 참가자 준수사항

참가팀은 WebSocket으로 음성을 주고받는 서버 하나를 만든다. 이 서버는 제공된 측정기가 보내는 손님 음성을 실시간으로 받아, 같은 형식의 음성으로 답해야 한다. 손님 말은 실제 말하는 속도로 들어오며, 말이 끝난 뒤에도 전화선처럼 무음이 계속 들어온다. 손님 말이 언제 끝났는지는 참가팀 서버가 스스로 판단해야 하고, 손님이 아직 말하는 도중에 답을 시작하면 그 문항은 실패로 처리한다.

응대는 제공된 상담 시나리오과 브랜드 정보를 따라야 한다. 시나리오와 브랜드 정보에 없는 정책을 지어내거나, 손님에게 받아야 할 정보를 받지 않고 기능을 호출하거나, 사람 상담원에게 넘겨야 할 상황에서 AI가 계속 응대해서는 안 된다. 주문 조회, 반품 접수 같은 기능은 쇼핑몰 시스템을 흉내 내는 모의 함수 서버를 통해 호출한다. 모의 함수 서버는 각 팀이 직접 만들며, 주어진 데이터로 맞는 결과를 돌려줘야 한다(SPEC.md). 호출 기록과 응답 지연은 측정기가 중간에서 맡는다. 호출할 때마다 해당 문항의 세션 번호를 함께 보내야 한다. 세션 번호가 빠진 호출은 채점에서 호출하지 않은 것으로 본다.

"확인해 보겠습니다, 잠시만 기다려 주세요" 같은 채움말은 첫 소리로 인정한다. 다만 조회 결과를 받은 뒤 실제 답을 시작하기까지의 시간도 따로 재서 속도 점수에 반영한다. 하나의 문항에 대한 응대를 모두 마치면 응대 종료 신호를 보낸다.

사용하는 모델은 행사 지원 모델이다: 받아쓰기(STT) Soniox `stt-rt-v6`(실시간), 음성합성(TTS) Gemini 3.8 Flash-Lite TTS(`gemini-3.8-flash-lite-tts`, 스트리밍 지원), AI(LLM) GPT-5.4 mini. 이용료는 각 팀 팀장 계정으로 지급된 크레딧으로 낸다. 이 모델들을 어떤 순서로 잇고 겹칠지, 말 끝을 어떻게 판단할지는 자유다. 개발과 연습은 각 팀 노트북에서 한다. 최종 측정은 제출한 압축 파일을 운영진이 자기 노트북의 컨테이너에 띄워 진행한다(7장).

제공 데이터는 실제 상담 기록에서 개인정보를 가짜 값으로 바꾼 것이다. 대회 목적 외에 쓰거나 외부로 옮기거나 공개해서는 안 된다. 비공개 시험 문항을 빼내거나 추측해 맞추려는 시도, 측정 중에 사람이 대신 답하는 것, 측정기의 동작을 우회하는 시도는 실격 사유가 된다.

## 4. 스코어링 방식

문항마다 응대 점수, 함수 점수, 속도 점수를 매기고 `시스템 총점 = 응대 × 0.5 + 함수 × 0.2 + 속도 × 0.3`을 낸다. 시스템 총점(100점)은 행사 전체 평가 중 "응답 품질 및 기능 구현" 20점으로 환산해 반영된다(시스템 총점 ÷ 5). 속도 점수는 첫 소리 기준 1.5초 이하 100점부터 0.5초마다 10점씩 내려가 6초를 넘으면 0점이고, 함수를 부른 문항의 조회 뒤 답은 3.5초 이하 100점부터 8초를 넘으면 0점까지 따로 매겨 둘을 평균한다. 자세한 기준, 계산 예시, 스코어보드 양식은 [SCORING.md](SCORING.md)에 있다.

## 6. 시작하기

```bash
pip install websockets httpx numpy scipy
python3 mock_tools/mock_server.py --port 8100                 # 모의 함수 서버 (lookup() 을 완성한 뒤)
python3 example_server/server.py --port 9000                 # 뼈대 서버 (여러분 서버로 바꿀 자리)
cd eval
python3 run_eval.py --server ws://localhost:9000 --mock http://localhost:8100 \
                    --cases ../data/practice_cases.jsonl --audio ../data/audio/practice --out runs/try1 --limit 20
python3 score.py --run runs/try1 --cases ../data/practice_cases.jsonl    # 함수·속도 점수 (키 필요 없음)
# OPENAI_API_KEY 가 있으면 응대 점수와 총점까지 나온다. 없으면 응대 채점만 건너뛴다
```

## 7. 최종 평가 진행

최종 측정은 **운영진이 직접** 한다. 시험 문항은 참가팀에 나눠 주지 않는다. 각 팀은 서버 코드를 **압축 파일 하나로 제출**하고, 운영진이 자기 노트북에서 팀마다 따로 만든 컨테이너(리눅스, 파이썬 3.11)에 띄워 잰다. 측정 때 팀 노트북을 켜 둘 필요도, 네트워크로 연결할 필요도 없다.

1. 18:30(Build & Finalize 끝)까지 압축 파일 하나를 제출한다. 담을 것과 형식은 아래 표를 따른다.
2. 운영진이 압축을 풀어 `requirements.txt`로 패키지를 새로 설치하고, `bash start_mock.sh <시험용 데이터>`와 `bash start_server.sh`로 두 서버를 띄운다. 시험용 모의 함수 데이터 `mock_db_test.json`은 운영진이 넣는다. 손님 말이나 정답은 들어 있지 않다.
3. 측정기가 시험 문항의 손님 음성을 상담 서버(9000번)로 보낸다. 상담 서버가 받는 `tools_url`은 측정기의 함수 중계 주소다. 함수 주소를 코드에 고정하지 말고 받은 `tools_url`을 그대로 쓴다.
4. 측정이 끝나면 운영진이 정답으로 채점해 시스템 점수를 낸다. 시스템 총점은 행사 평가의 20점으로 환산된다(÷5).
